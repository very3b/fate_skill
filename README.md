# fate_skill

> **把一颗芯片的 datasheet，变成一个能上机跑的 ATE 测试工程。**
>
> 这是**跨厂家、跨 DUT** 的能力。
> ATE 开发不会再有新增岗位了——因为它已经变成一个 skill 就能解决的事情。
> 新人剩下的核心价值，只有一件事：**懂测试设备的原理**，而不是会写某一家 IDE。

WorkBuddy / Claude Code 技能仓库。

每个技能是一个独立目录，含 `SKILL.md`（入口）+ `scripts/`（可执行脚本）+
`references/`（按需加载的参考资料）。

## 这是什么：一个课程项目

这不是厂商 SDK 的包装，也不是某个公司的内部工具。

**它来自一门面向零基础学生的 ATE 实践课。**

一门职业技术院校的集成电路测试课程，学生在大二，
实验室里摆着万用表、示波器、直流电源，和一台真实的 ST2500 ATE。
课程主线是 **元器件 → 仪表 → ATE → 可靠性 → 综合项目**。

学生要在课上真正上手：从器件手册提限值、设计测试项、
编 pattern、写测试程序，最后在真机上跑出 Bin。

> **顺便说明：加速科技只是我们恰好手头有。**
> 实验室里摆着 ST2500，所以第一个 skill 从它做起。
> 但主角不是它——**是方法**。
> 手边换成别的机器、别的厂家，这套东西照样该成立。

### 为什么会有这个仓库

第一轮课，学生卡住了。卡点出奇地一致：

- 手册只说"支持多种波形格式"，不告诉你 RZ 和 NRZ 到底差在哪个边沿
- IDE 的 import 按钮莫名其妙变灰，没人知道原因
- `g++` 一调用就崩，退出码 1，连报错都没有
- 测出来了，但报告上的数是错的——因为漏调了一次判限

**这些坑，官方文档里没有，老师课上也不会逐个讲**
（因为太琐碎，一次课讲不完，而且下堂课就忘了）。

于是我们把每一个卡点都查到了根因：翻官方 CHM 手册、对照教学课件、
**反编译 IDE 插件**看它到底怎么判定的、读 `.tim`/`.pat` 源码、
在真机上一个一个实验验证。

然后把这些答案写成了一个 skill。

### 这件事的意义

**一个 0 基础的大二学生，跟着 skill 走，能从零搭出完整可上机的测试工程。**

这在以前需要一位资深工程师手把手带两周。
现在只需要一个下午，和一个愿意把话说清楚的 skill。

更关键的是——**这套东西是可复制的**。

课程年年开，学生年年换，坑却永远是那几个。
把它们沉淀下来，下一届就不用再踩一遍。

这也是这个仓库存在的全部理由：
**把老师踩过的坑，变成学生不用踩的坑。**

## 先说三件让人生气的事

如果你上过 ATE（自动测试设备）的培训班，或者正准备进测试岗，这三件事你一定遇到过。

### 一、ATE 是行业的边角料，然而每家公司居然都在自建生态圈

ATE 本身是个小众赛道：门槛高、投入大、圈子窄。

于是乎每一家设备厂商都自己造了一套轮子——自己的工程文件格式、自己的 IDE、
自己的 API 命名风格、自己的"最佳实践"。学完 A 家的，换到 B 家，
**语言是新的，习惯是新的，坑是新的**。

学习成本被生态碎片化放大了，开发成本被重复造轮子推高了。
而这一切，本质上不是因为测试原理复杂。

### 更别提它配套的资料有多不靠谱

厂商给的**培训材料错误很多**，给的**开发资料遮遮掩掩**。

培训 PPT 里让你照着抄，抄完发现跑不通——因为那页图和实际软件版本对不上。
API 手册翻到想用的那章，参数表列了一半，关键的默认值语焉不详。
问技术支持，得到的回答是"请参考我们提供的示例工程"，
而那个示例工程里恰好没有你要用的功能。

于是新手只能靠**猜 + 试 + 憋**。
一个参数猜错了，报错信息还看不懂（或者根本没有报错），
一晚上就过去了。

### 说句得罪人的话：ATE 没那么神秘

剥掉那层专业外壳，ATE 干的活你其实都会：

- 一堆可编程的 IO 引脚，驱动电平、比较电平
- 一个时序发生器，按周期往引脚上打波形
- 电源通道，可编程设电压、限流
- 一点测量能力，测 VOH/VOL、漏电流、阻抗
- 一个能把上面这些按顺序跑一遍、并给出 Pass/Fail 的流程引擎

**说白了，ATE 就是一块给单片机开发板，只不过外面装了一个大铁壳子。**

你在开发板上写个循环读 ADC，ATE 干的也是同一件事——
只是把"读 ADC"换成了"在被测器件的每个管脚上按图样放电平、然后量结果"。

真正难的从来不是**设备**，是**你手里那颗芯片到底该怎么测**。
而这恰恰是所有厂商都不愿意告诉你、因为那属于他们核心 know-how 的部分。

那部分知识，本该是公开的。

### 二、测试设备支持 SCPI 是行业共识，ATE 却背离了它

示波器、源表、程控电源……全世界的测试测量仪器都在往 **SCPI**
（可编程仪器标准命令集）上靠。

`*IDN?` 问你是谁，`OUTP 3.3` 设电压，`MEAS?` 读回值。
仪器之间互相理解，脚本跨平台迁移，实验室自动化唾手可得。

**然后你打开 ATE。**

没有 SCPI。有的是"必须连着这家的机台、装这家的软件、
才能跑通这套流程"。

一个明明在测同一个物理世界、明明握着同一批被测器件的领域，
硬生生把自己隔离在标准之外。
这不是技术难度决定的，是商业封闭策略决定的。

### 更不该的是：把这种东西搬进大学课堂

**私有、封闭、脱离开放标准的技术，本就不该出现在大学课程里。**

大学课程该教的是**这个行业公认的、开放的、能带走的知识**：
测试原理、测试项设计方法、时序与信号完整性的物理基础、
自动化测试的通用方法论。

而 ATE 现状是什么？是每家厂商一套私有格式、一套私有 IDE、
一套私有 API，还附带一堆写错的培训材料。

于是大学课程被一种奇怪的方式绑架了：

**课程变成了某家公司的产品广告课。**

- 教材是厂商的培训 PPT，老师讲的是厂商的"最佳实践"
- 考核的是"这台机器的工程文件怎么填"
- 学生练熟的是这一家的 IDE，不是这个行当
- 换一家厂商，课程内容整体作废

这不是教学，这是**渠道**。
学校免费替厂商做市场推广，用的是学生的课时和学分。
而学生付出的是本该用来学原理的时间。

**这不是贬低具体某家公司**——每一家的设备确实有真本事。
问题出在**商业模式决定的技术形态**，恰好被原样搬进了课堂。

值得警惕的副作用是：学生产生了一种错觉，
以为"会用这台机器"就是"会做测试"。
毕业换个平台，从零开始。

那门课本该给他们的是**能力**，结果给的是**工具**。
工具会过期，能力不会。

### 那怎么办

只有一条路：**把厂商的产品降级为"教具"，把原理提升为"教材"。**

具体说：

- 手上这台机器，是用来**理解时序、限值、测试项设计**的教具，
  不是用来背诵"这个文件怎么填"的模板
- 讲这门课的老师，**至少要懂原理，并且敢于指出厂商资料里的错误**
- 学生带走的是**方法**，机器只是**验证方法的地方**

判断一堂课是不是广告课，有个粗暴但管用的标准：

> **把厂商换成另一家，这门课还成立吗？**
>
> 如果不成立——那它教的不是知识，是操作手册。

这也是本仓库存在的另一层理由：
**它不教你怎么用加速科技，它教你怎么做测试。**
平台只是当下的教具，原理才是能带走的东西。

### 三、AI 时代，"会写 ATE 程序"这项技能本身正在贬值

看这个仓库里第一个技能干成了什么：

给它一份 74HC138 的 datasheet 和一台 ST2500，它输出——
十个工程文件、一份 Test.cpp、28 个 pattern、51.7 万行向量、
自动化校验脚本 —— **AI 一次跑完**。

这在五年前是一个资深工程师两到三周的活。
现在是一个下午。

**所以结论很残酷，也很有机会：**
"会写某家 ATE 的测试程序"这项能力，正在快速贬值。
岗位不会因为 AI 而消失，**但会因为这件事被自动化而不再需要人手**。

那新人靠什么立住？

## 划重点：新人真正该练的是什么

不是熟练某家的 IDE，不是背下某家的 API 名字，
不是知道 `.tim` 文件第几行该填什么。

**是理解测试设备在物理层面到底在干什么。**

比如：

- 你的 Pattern 里写一个 `0`，它到底是"输出低电平"还是"输出一个脉冲"？
  → 答案是**取决于信号**，取决于波形表里的槽位定义。搞反了，整套时序全废。
- 测 `VOH` 的时候，那个脚到底是该被选中还是不选中？
  → 取决于器件是**低有效**还是高有效。搞反了，测出来的是别人的数。
- 你以为测出来了就有用？
  → 漏调一次判限函数，测出来的值**根本不会进 Bin**，报告上还一切正常。

这些不是某一家的知识点，是**测试工程的物理逻辑**。
换个厂商照样成立，学一次终身受用。

而这套逻辑现在是能被 skill 完整传递的。
**工具层面交给 AI，原理层面留给自己。**
这才是 AI 时代一个 ATE 新人该有的姿势。

## 技能列表

下面这些 skill 都在做同一件事：
**吃进一份 datasheet 和一台 ATE，吐出一个能上机跑的测试工程。**
区别只在于覆盖哪家设备、哪类 DUT。

**每个 skill 都分两层**：
上层是与厂商无关的**方法论**（怎么从手册提限值、怎么设计测试项、
怎么把激励和向量对上器件行为），
下层是针对该厂商的**适配**（文件格式、API 调用、IDE 行为）。

换厂商，换的只是下层。

### `st2500-ate-project` — 加速科技 ST2500/ST5000 ATE 测试工程

> 这是第一个 skill，因为实验室恰好有这台机器。
> 它是**方法论的一个实例**，不是这个仓库的边界。

为加速科技 ST2500 / ST5000 ATE 测试机**新建、调试或修复**完整测试工程。

> 一句话：**把"查手册 + 踩坑"这件苦差事，压缩成一次对话。**

覆盖的工程文件（缺一不可）：

| 文件 | 作用 |
|------|------|
| `X.job` | 工程入口（JSON），指向其余所有文件 |
| `X.sig` | 信号→通道映射 |
| `X.grp` | 信号分组（决定 `pinlevel` 能否单独给某脚施压） |
| `X.res` | 机台资源表（板卡 OnLine 与数量） |
| `X.tim` | 波形表（TimingSet / WFC 槽位 / Evt 边沿） |
| `X.pat` | pattern 索引（名字 → CSV 相对路径） |
| `X.tmf` | 测试流（顺序 + Sbin + 限值） |
| `Test.cpp` | 测试逻辑（导出函数） |
| `pattern/*.csv` | 向量文件 |
| `Makefile` | 编译生成 `Test.dll` |

#### 核心内容

- **8 步工作流**：读手册提限值 → 核资源 → 设计分组 → 写时序 → 写 pattern
  → 写测试代码 → 写测试流 → 编译
- **Pattern / WFC 时序方法论**：两套编号体系（槽位名 vs Evt 边沿序号）、
  字符集硬约束、RZ/RO/NRZ/SBC 四种信号格式与 Wave Table 自由拼装
- **ST-IDE 导入机制**（插件反编译实证）：import 变灰的三个根因
- **编译环境**：本机 g++ 不可直接调用的原因与三条可用路径
- **测试方案方法论**：从器件手册到测试项矩阵，VIH/VIL 二分搜索测法

#### 两个实用脚本

```bash
# 工程交叉校验（5 项检查）
python st2500-ate-project/scripts/validate_project.py <工程目录> [--truth-table]

# ST-IDE 导入预检（打开 IDE 之前就发现问题）
python st2500-ate-project/scripts/check_import_ready.py <工程目录>
```

`validate_project.py` 检查：

1. Pattern 字符 ⊆ `.tim` 的 WFC 集合（硬约束，违反则运行时加载报错）
2. `.pat` 索引完整性（注册了但文件不存在 = 静默不加载）
3. `.tmf` 函数名 ↔ `Test.cpp` 导出函数
4. `.tmf` 参数数 ↔ 实际判限调用数（**漏调判限 = 测出的值不会被判限**）
5. 译码真值表自洽性

已在 5 个工程回归通过（74HC138 / ADC0832 / HK32F031 / HK24C02 / LM358P）。

## 这个仓库想干什么

### 一句话

**把一颗芯片的 datasheet，变成一个能上机跑出 Bin 的 ATE 测试工程。**

### 为什么值得做成一个 skill

因为这条链路上，**每一段都不难，但整条链路没人教**：

```
datasheet                ← 一堆表格：电气特性、时序参数、功能真值表
   ↓  提取限值、设计测试项矩阵
测试方案                  ← 测哪些项、怎么激励、限值多少、怎么分 Bin
   ↓  信号分组、波形设计
ATE 工程文件              ← .sig / .grp / .res / .tim / .pat / .tmf
   ↓  写测试逻辑
Test.cpp + pattern/*.csv  ← 向量与判限
   ↓  编译、上机
Bin 报告                  ← 器件到底合格不合格
```

每一段单独看都不算难：
查手册会、画表格会、写 C++ 会、编 CSV 会。
**难的是把它们接起来，并且每一步都不出错。**

而现有工具帮不上忙：
厂商给的是**某一家的操作手册**，
不是**"从 datasheet 到 ATE 工程"的通用方法**。

### 三条必须同时成立的性质

**一、跨 DUT。**
今天测 74HC138，明天测 ADC0832、后天测 MCU、EEPROM、运放。
**DUT 换了，方法不应该重写一遍。**
真值表类的器件，测项矩阵可以自动推导；
模拟参数类的器件，需要一套通用的测量方法论。
这才是 skill 存在的意义——**它记的是方法，不是某一个器件的答案。**

**二、跨厂家。**
每家 ATE 的文件格式、API、IDE 都不同，
但**"驱动-比较-测量-分 Bin"这套骨架是一样的**。

做法是：把厂商的私有生态**拆开、还原成原理**，
再把原理装进 skill，把厂商差异收进薄薄一层适配。

**加速科技、Chroma、Accotest、Teradyne……在这套结构里地位是一样的**：
都只是"恰好手边有"的那台机器，都是适配层，不是主角。

学生换厂商，换的是那层适配；**方法论那一层不动。**

**三、跨 AI 与人。**
工具层面交给 AI：读手册、生成工程文件、写 pattern、跑校验。
原理层面留给人：判断这个器件该怎么测、这个激励对不对、
这个数是不是在物理上说得通。

**AI 负责执行，人负责判断。**
这也是唯一能同时跑出速度和正确性的分工。

### 现在到哪一步了

**先说清楚一件事：加速科技不是主角，它只是我们恰好手头有的那台机器。**

实验室里摆着 ST2500，所以第一个 skill 从它做起。
这不是因为它更好、更标准、更值得支持——
纯粹是因为**这是我们手边唯一能真机验证的设备**。

> 换个实验室、换台机器，这套方法应该照样成立。
> 换了之后要改的，只是那薄薄一层适配。

第一个 skill 跑通了 **加速科技 ST2500/ST5000 + 一批真实 DUT**：

| DUT | 类型 | 覆盖 |
|-----|------|------|
| 74HC138 | 数字组合逻辑 | OSN/OSP/IIL/VIH/VIL/VOH/VOL/IDD/功能测试 |
| ADC0832 | 模数转换 | 时序驱动型功能测试 |
| HK32F031 | MCU | 电流类参数（上下拉） |
| HK24C02 | EEPROM | I²C 协议型功能测试 |
| LM358 | 运放 | 模拟参数测试 |

覆盖了数字、模拟、混合三类器件的测试项设计。
验证脚本已在 5 个真实工程上回归通过。

**下一步：**
换一家设备厂商（Chroma / Accotest / Teradyne…），
验证"跨厂家"这条性质真的成立；
再往更复杂的 DUT 走（MCU 内部资源、存储器可靠性、模拟前端）。

当第二个、第三个厂商接进来的时候，
大家会发现留下来的那个**骨架**才是真正的东西——
而它跟加速科技一点关系都没有。

### 一句话收束

**一家厂商的封闭生态，注定培养不出懂原理的人——它只培养出懂这一家的人。**

而这仓库要做的是反过来的事：
把厂商的私有工程实践，翻译成**任何人、任何 DUT、任何设备都能用的方法**，
再交给 AI 去批量执行。

**这些是原理。原理不认厂商，也不认具体芯片。**
